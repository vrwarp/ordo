# Review of the prototype, 2026-11-03

Scope: the whole implementation as of commit `598069f`, after all three milestones were built. Method: four
independent reviewers, one per area (hub and deploy; renderer and output window; operator app; importers,
audio, surfaces, stage and shared packages), each verifying findings by running the built apps against real
hub processes in headless Chromium, plus the coordinator's own checks. The end-to-end suite was repeated three
times (12 of 12 passed) and all 235 unit tests pass.

Verdict: the architecture holds up and the core service flow works end to end, including a hub outage.
The prototype is not ready for a live service until the items marked **Fix before the first service** are
done. Nothing found is structural; every item has a concrete fix.

Each finding states how it was verified. "Verified" means a reviewer reproduced it with a script or test.
"Plausible" means it was established by reading the code but not reproduced.

## Fix before the first service

### 1. Outputs stuck on the fallback bus after the operator tab goes away (high, verified)

`packages/client/src/link.ts:46-49, 61-65`. The only way an output leaves fallback mode is a `fallback.hub`
message from the same operator page that put it there. If that page closes or crashes while the hub is
down, the output ignores the hub for good once it returns. A new operator tab cannot reach the window by
name either, so Relaunch opens a second window while the stale one stays on the projector.
Reproduced: hub killed, operator became authority, operator tab closed, hub restarted; the output reconnected
but stayed on the fallback bus and ignored hub GOs and a new tab's keys.
Fix: outputs leave fallback on their own when the hub socket is up and the hub's state sequence is at or
above theirs, or when no fallback traffic has arrived for about 5 s (have `FallbackHost` re-announce to ready
windows as a heartbeat), or when `window.opener.closed`. The operator should also post `fallback.hub` to every
window it acquires while in hub mode, and warn when Relaunch could not close existing windows.

### 2. Silent hub death takes 55 to 60 s to notice (high, verified)

`packages/client/src/hub.ts:146-153, 172`. Ping every 10 s, close only after the fourth unanswered ping,
then `ws.close()` waits for a handshake on a dead connection. The design promises 30 s plus a 5 s grace.
Reproduced with a frozen TCP proxy: "Hub reconnecting" after 55.6 s, fallback authority after 60.6 s. During
that minute the operator applies keys optimistically while the outputs do not change.
Fix: on liveness failure mark disconnected immediately and discard the socket (`onclose = null; close()`);
three misses; a shorter interval while live (3 s ping, 3 misses, about 10 s). The same class serves outputs.

### 3. Hub connection flaps whenever pong latency exceeds about 90 ms (high, verified)

`packages/client/src/hub.ts:120-128, 150-157`. After `welcome` the client fires four pings 30 ms apart to
seed the clock, but each increments the unanswered counter and the fourth closes the socket if the first pong
has not arrived within 90 ms. Backoff resets on welcome, so it reconnects and repeats. Reproduced with a fake
socket: a 120 ms pong delay gives three sockets in 1.5 s with status flapping. Any hub stall at connect time
(a synchronous import, a backup, a busy NAS) or a slow reverse proxy triggers it, and each flap makes the
operator switch buses and resync.
Fix: do not count the seed burst towards liveness, and judge liveness by time since the last pong.

### 4. Section buttons act on the live item, not the item on screen (high, verified)

`apps/operator/src/views/live/SlideGrid.tsx:743-744, 829-830`. The grid sends `goToSection(i)` with an index
computed in the viewed item; the reducer resolves it against the live item. With song 2 live and song 1
shown (Follow live off), clicking song 1's Chorus went to song 2's Chorus.
Fix: the grid knows the cue index; send `go(cueIndex)`. Keep `goToSection` for Stream Deck and MIDI, where
live-item semantics are intended.

### 5. Nightly backup re-fires every second for an hour after 03:00 (high, verified)

`apps/hub/src/backup.ts:56-68` with `packages/domain/src/time.ts:6-15`. `nextTimeOfDay` deliberately
returns up to 60 minutes in the past (meant for countdown display), so after the 03:00 run the next delay is
1 s, and so on until 04:00: thousands of full database copies per night, also whenever the hub starts
between 03:00 and 04:00. Reproduced with a fake clock: four backups in 4.5 s.
Fix: schedule strictly after now (add 24 h when the computed time is within a minute of now), skip the run
when today's backup exists, minimum delay 60 s.

### 6. Lyrics parser drops a repeated section whose lyrics differ (high, verified)

`packages/domain/src/lyrics.ts:97-108, 195`. A second `Chorus` with different text is discarded and the
arrangement repeats the first. SongSelect exports and pasted lyrics do this routinely.
Fix: compare the stanzas; if different, create the next free numbered section (`Chorus 2`) and use it in
the order.

### 7. ProPresenter zip import inflates the whole archive into memory (high, plausible)

`apps/hub/src/imports.ts:149`, `packages/importers/src/zip.ts:60-83`. Every entry including videos is read
into a map with an 8 GB budget, inside a container limited to 4 GB. A real library export with motion
backgrounds will kill the hub, and if it happens on a Sunday the outputs lose the hub. The NAS folder path
already avoids this by leaving media on disk.
Fix: stream media entries to temp files (or skip inflating entries with media extensions and resolve them
lazily) and cap the in-memory import at a few hundred MB, telling the user to use the folder path for large
libraries.

### 8. OPFS cache wiped on End service and re-downloaded on the next Go live (medium, verified)

`apps/output/src/app.ts:709-736, 787-798`. With no live playlist the manifest is fonts plus logo, the fill
finishes instantly and the prune deletes every media file. Observed: 5 files while live, 1 after End
service, 4 fetched again on the next Go live. At launch the fonts-only fill races the hub's first state.
Fix: never prune on an idle manifest; prune only while live, against the union of recent manifests or a
size budget; skip the fonts-only fill until the first state arrives.

### 9. Placement dialog on every Launch for single-screen setups (medium, verified)

`apps/operator/src/lib/screens.ts:66-69`, `services/outputs.ts:118-127`, `views/live/LiveDialogs.tsx`.
Unmatched outputs are never saved, and "Leave on the main screen" only closes the dialog, so a modal covers
the live view at every service start and after every Relaunch.
Fix: save the primary screen for those outputs; skip the dialog when there is one screen.

### 10. Video that fails to load once is never retried (medium, plausible)

`apps/output/src/media.ts:71, 103`. The rejected load promise stays cached, so every later arm of that cue
returns the same rejection. A single slow read from the NAS or OPFS makes that cue un-armable for the rest
of the service.
Fix: clear the cached promise when a load fails; `unload()` is never called today.

### 11. Wake lock lost after the first occlusion (medium, plausible)

`apps/output/src/main.ts:66-81`. Chrome releases the sentinel when the window is hidden or covered (a dialog
or ProPresenter over the output); the variable stays set, so the visibility handler never re-requests.
Fix: listen for the sentinel's `release` event, clear the variable, re-request on visibility.

### 12. 30 Hz displays report missed frames forever and flip late (medium, verified)

`packages/renderer/src/timing.ts:70-76`. The vsync estimate only learns from gaps under 25 ms, so a 30 Hz
TV (common for 4K over HDMI 1.4 in a lobby) counts every frame as missed and lands flips a frame late half
the time. Reproduced with 33 ms gaps: 299 missed of 300.
Fix: establish the frame period from the median of the first gaps before counting misses.

## Requirement gaps against the PRDs

- **prd/03** "Send to preview" to an idle output: not implemented (no hub or output path).
- **prd/02** Clear all "or hold": only the double press is implemented.
- **prd/08** Cache integrity check at Launch outputs: nothing runs at Launch; only each output's fill progress is shown.
- **prd/08** Per-window log lines in diagnostics: the protocol carries no output logs.
- **prd/04** Lower-third look has no per-item "show media" option; the stage look does not render video remaining time.
- **prd/02** Usability: 19 of 28 live-view controls are 28 px high; `.muted` text is below 4.5:1 contrast at 11 to 12 px.
- **design/14** Golden-image tests of the text rasterizer were not written.

## Needs investigation on real hardware

These cannot be settled in this container, which has no GPU and no Docker daemon:

1. The WebGPU path (`packages/renderer/src/gpu.ts`) has only been reviewed by reading; every run here fell
   back to Canvas 2D. The venue PC must show the `webgpu` compositor in the diagnostics overlay and pass the
   60-minute soak.
2. Autoplay with sound in a popup window: the code degrades to muted playback with a message, but the
   Chrome policy on the venue PC must be confirmed (and documented in deploy/README.md).
3. The Docker image: Dockerfile and runtime layout verified by simulation only; the arm64 build relies on
   prebuilt native modules under QEMU.
4. Synology DDNS subdomain resolution and the DSM wildcard certificate.
5. Two hot-path costs to measure in the soak: the per-state IndexedDB save of the full live state on the
   output main thread, and the program-view snapshots at 10 Hz on the WebGPU canvas.
6. Audio device selection on Chrome versions below 110 and with a device that lacks the expected channels.

## What was checked and found solid

- Role matrix and tokens: edit cannot control live or see tokens; an output token reads only its own config;
  PIN rate limit and lockout; cookie flags; forwarded-header trust; security headers and CSP against what the
  built apps actually load; WebSocket origin check and unauthenticated-socket handling; per-socket overflow
  recovery.
- Live service: goLive refusals, 423 locks and their release, journal and snapshot recovery after SIGKILL
  (timers, messages and loop auto-advance resumed), resync on gaps, adopt rules.
- Media pipeline: every format converts; corrupt files fail cleanly with retry; range requests; transcode
  resumes after a crash; backups and the restore CLI work end to end.
- Output path: frame loop allocates nothing beyond WebGPU-mandated objects (enforced by a lint test); arm
  and flip under rapid GOs, past `at`, clear-all, background crossfades and fades in progress; video hold,
  advance, black, loop, pause and restart; audio only on the master; service cache fill order, atomic writes
  and zero re-downloads on relaunch; props in the venue time zone; every look's visibility rules; the stream
  key colour never fades; the service worker never caches `/api` or `/ws` or tokens.
- Operator: GO flow and pre-arm, the full key map, double-press clear-all, optimistic rebasing with
  rejection rollback, fallback authority within 5 s of a hard kill with adoption on return, conflict dialog,
  launch and relaunch, playlists, library, editor save with 409 handling and revisions, settings pages, no
  console errors across the runs.
- Importers: RTF reader edge cases, ProPresenter geometry and arrangements, nested bundles and zip safety,
  SongSelect and ChordPro basics, PPTX placeholder inheritance and tables; audio routing lands a stereo source
  only on its pair; Stream Deck and MIDI driver usage matches the library APIs; stage display timers,
  messages, flips and offline start.

each one and, for the link failures, new end-to-end scenarios. The suites after the fix pass: 380 unit
tests, 7 end-to-end scenarios, the golden-image rasterizer check, lint and typecheck clean.

Two things changed from the proposed fixes:

- Finding 1's "new tab takes over the stale window" cannot be done from the operator: Chrome resolves window
  names only within one browsing-context group. Instead the hub sends `bye superseded` to an older socket
  when a newer window with the same output id connects, and the old window closes itself.
- Finding 2's target of 12 s to fallback authority became 14 to 15 s: 9 s to declare the hub lost plus the
  5 s grace in the operator. The grace is one constant if a shorter time is wanted.

One gap stays open by decision: a per-item "show media" option for lower-third looks needs a playlist-item
field as well as a look rule, so it is a domain change for a later milestone.

What still needs real hardware is unchanged: the WebGPU compositor, the venue soak, Synology DNS and
certificate, the Docker build, and audio device behaviour on the venue's interface.
