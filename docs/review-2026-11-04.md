# Review of the hardening pass, 2026-11-04

Scope: the isolation and hardening work (design/25, ADR 0014) as of commit `d295d6e`. Method: four
independent reviewers, one per area (hub processes; output window and renderer; operator core worker; stage,
parser fuzzing and spec conformance), each verifying by running the built apps and real hub processes in
headless Chromium with their own scripts, plus the coordinator's checks (suites, the supervised hub in the
Docker runtime layout with a killed library child, the soak tool against the two-process hub).

Verdict: the architecture is in place and most of it holds under chaos. The suites pass (527 unit tests,
28 of 28 end-to-end across two runs, golden images, lint, typecheck). But the review found four high
findings, three of them on the audience path, that undo part of what the hardening set out to guarantee.
They must be fixed before the first live service. Every finding below names its evidence and fix.

"Verified" means a reviewer reproduced it; "plausible" means established by reading, not reproduced.

## Fix before the first service

### 1. The audience sees black during a render-worker restart (high, verified)

`apps/output/src/host.ts:581-583, 662`, `packages/renderer/src/engine.ts:404`. The hold image is an
`ImageBitmap` created inside the render worker from that worker's canvas. When the supervisor restarts the
worker, the bitmap is backed by a dead context and draws nothing, so the hold canvas is transparent and the
new canvas fades in from black. Sampled at 20 ms: navy slide until 3.0 s, transparent hold at 3.1 s,
black at 3.2 s, a 300 ms fade from black, content back at 3.6 s. The same mechanism was already found and
fixed for the asset worker. This also defeats the crash-only "no frame for 3 s" restart path.
Fix: keep a main-thread copy. On every snapshot message draw it into a main-thread offscreen canvas (at
most seven per second), or `createImageBitmap(bitmap)` on the main thread and keep that; the hold must be
painted before the worker is terminated.

### 2. A video's end is lost across a link-worker restart (high, verified)

`apps/output/src/host.ts:369, 390`. Media element events go to the current link worker; between its death
and the restart they are posted to a dead worker, and the new generation re-arms the same key without
replaying what the elements already did. A 3 s clip with the link killed 0.9 s in: the element reports
ended, the hub still says playing 6 s after the restart. With `onEnd: advance` the service never advances.
Fix: include per-slot `ended`, `paused` and `currentTime` in the host status, and have the restarted link
synthesise the ended event for a live, playing, non-looping media whose element has ended; or queue media
events on the host while no link generation is alive and replay them.

### 3. A transient file outage quarantines good cues for the whole service (high, verified)

`apps/output/src/link-core.ts:736, 713, 1389`, `asset.worker.ts:81-86`. Every arm failure counts toward
quarantine, including "failed to fetch" for a file not yet cached and a media element error while a video
streams during an incomplete fill; the third strike lands about 6 s after the first. A 14 s outage of the
file route on a fresh output quarantined the background and both video cues; after the cache filled 5 of 5,
the background stayed empty while health reported `armedOk: true`, because quarantined keys map to "not
required". A slow NAS at service start, when videos are the last files filled, produces exactly this.
Fix: only deterministic failures (decode or raster errors) count toward quarantine; unavailability gets
exponential backoff and never quarantines; lift unavailability entries when the fill completes; a
quarantined required key must make `armedOk` false.

### 4. Settings changes reach outputs stale (high, verified)

`apps/hub/src/liveproc.ts:833-836`, `librarylink.ts:1320-1324`. The live process broadcasts the settings
delta before refreshing its own copy of the library context (a 50 ms debounce then a fetch). The output
refetches its config at once and gets the old look: old name at +7, +31 and +53 ms, new one from +76 ms. A
look, audio or output change made by the operator is silently not applied on the audience screen until
the next unrelated settings change. A regression from the single-process hub.
Fix: refresh the context first (bounded), then broadcast; and have outputs refetch their config on every
`welcome`.

### 5. An expired session turns the operator into the fallback authority against a healthy hub (medium, verified)

`apps/operator/src/core/engine.ts:277-281`, `packages/client/src/hub.ts:331-338`. On `bye unauthorized`
the worker reconnects every 5 s and is refused each time; the only host-side handler reacts to `version`;
the socket being down while live arms the fallback grace. After clearing cookies and restarting the hub:
authority `fallback`, both outputs on the bus, "Hub lost: running from this PC", a toast every 5 s, and no
sign-in path without a reload.
Fix: treat `unauthorized` and `forbidden` as not a hub loss: stop reconnecting, do not arm the grace, route
to the login view, one persistent banner.

### 6. A 200 KB PowerPoint can grow a worker to 2 GB (medium, verified)

`packages/importers/src/pptx.ts:217-219, 249`, `apps/hub/src/pool.ts`. Zip parts are inflated without a
size bound and the CPU pool's workers have no `resourceLimits`. A 205 KB file whose slide holds a 200 MB
text node ran 84 s to a worker out-of-memory; the library process's memory climbs by gigabytes first, which
invites the kernel's killer inside the container limit. Related: 300,000 shapes on one slide cost 8.5 s and
1.1 GB; 100 MB of RTF `\par` costs 618 MB.
Fix: check each part's declared uncompressed size before inflating (reject over about 8 MiB per part and
64 MiB per archive), cap text per run, and give pool workers `resourceLimits` of a few hundred MB so a
runaway parse fails in seconds inside its own heap.

### 7. The hub chaos test does not assert the screen held (medium, verified by reading)

`e2e/chaos-hub.spec.ts:66-68`, and the same gap in `chaos-output.spec.ts:148` and
`chaos-operator.spec.ts` test 1. After a kill, the cue is read once before the window could have noticed,
then the test waits for recovery. The output spec's "never black" window ends before the supervisor's 3 s
dead timeout, which is exactly when finding 1 goes black. Fix: sample the held cue and a pixel at about
100 ms for the whole restart window, until restarts have incremented and the hold has come down, and compare
to the pre-kill value.

## Chaos coverage against design/25

Covered: kill a worker (output, operator, stage), corrupt an OPFS file, send a malformed delta, kill either
hub process, corrupt a snapshot, flood a socket, freeze a socket. Not covered: exhaust storage quota, revoke
the GPU, a core restart while the operator is the authority or during adoption (both verified by hand and
pass), session expiry, a slow or failing IndexedDB, the hub stall watchdog and the library "failed" state.
Several specs assert the end state rather than the audience screen throughout (finding 7).

## What was checked and found solid

- Hub processes: the internal secret cannot be bypassed or found in logs; the proxy handles cookies,
  7.7 MB multipart with 100-continue, HEAD, 304, ranges and byte-exact downloads; a library killed
  mid-upload gives the client a 503 with Retry-After and is back in 1.5 s; a stopped live process is killed
  by the watchdog at 5.5 s and back at 7 s with its state; budget exhaustion reports `library: failed` while
  the live API keeps answering; journal and snapshot migration from a single-process data directory; sessions
  valid in both processes with logout closing sockets within 30 s; SIGTERM ordering; WebSocket caps against
  real traffic; strict schemas against the operator's real requests; validated restore with two previous
  snapshots; job attempts decrement on a clean stop so three deploys do not fail a transcode; Dockerfile,
  arm64 assumptions and CI.
- Output window: the frame loop still allocates nothing; a GO adds no main-thread work; restarts re-wire
  every port with generations, re-arm live and armed, keep a video playing across a render restart, converge
  during a crossfade; OPFS partial files never appear under the real name; clamps are inclusive at their
  bounds and run before any job; health fields validate against the hub schema; the soak tool's telemetry
  fields are present; port offers from a foreign tab are rejected; the opener check runs on the 250 ms tick.
- Operator: keydown to optimistic view in 5 to 22 ms with a 5,000-presentation library; IndexedDB is not on
  the GO path; exactly-once across core restarts in hub mode, fallback mode, during adoption and right after
  goLive; the view model never shows a live slice against a stale resolved playlist; one port per window;
  no listener growth across restarts; the supervisor ignores heartbeats during its own stall; red states and
  the checklist agree.
- Stage: no long tasks on the main thread ever; clock, message TTL and fades exact; worker kill, live-process
  kill, hub kill with reload and offline start all hold the lyrics; fonts retried with a bound; port handoff
  and request after a restart work.
- Fuzzing: the properties assert the documented bounds and the Zod schemas; the generators reach labels,
  directives, RTF control words and protobuf field variety; adversarial inputs (10 MB lyrics, 2 million
  nested RTF groups, 100 MB RTF strings, 1 GB and 600 MB zip entries, lying central directories, 20,001
  entries, nested bundle bombs) are bounded in time and memory except finding 6.

### The two limits, settled (2026-11-04, later)

Both "things to know" above were put to experiment (design/14, "Abrupt worker death", has the numbers).

**Slide images that cannot be read were not a limit.** Backgrounds and media already re-armed when their file
arrived; slide images were left out. They now draw without the image and the key is refreshed in place, with
no flip, when the file arrives. Health reports keys drawn without images. A chaos step withholds a slide
image until after GO and checks the slide fills in within about 800 ms with the cue unchanged and no black.

**The abrupt render-worker crash is a narrower case than stated, and the obvious fix is worse.**
Measured in headless Chromium with 2D and WebGPU canvases:

| Death mode | What the placeholder canvas shows | Signal to the host |
| --- | --- | --- |
| Uncaught exception | Keeps drawing (the worker is not killed) | `error` in 2 to 3 ms; the supervisor raises the hold before terminating, no gap |
| Out of memory, 2D | Worker survives 9 s of allocation; frame kept | none needed |
| Out of memory, WebGPU | The whole renderer process dies; the page is gone | nothing in-page can help; the output relaunches from IndexedDB |
| Hang | Frame kept | heartbeat; hold covers |
| Bare `terminate()` with no hook | White within 30 to 70 ms, 4 of 6 runs on WebGPU | none; only the chaos hook does this |

So the only death that can show white is one the product never performs. The proposed cure, presenting
every frame through a main-thread canvas, was prototyped and rejected: an `ImageBitmap` handed over with
`transferToImageBitmap` stays backed by the worker's context and goes white on the same deaths (6 of 6 on 2D),
so only a per-frame `drawImage` copy on the main thread survives, and that puts the audience picture on the
host thread: with back-pressure this machine committed 136 of 288 frames at 1080p, and a stalled main thread
would freeze the picture. That trades a flash that only a test can cause for dropped frames under any
main-thread stall, against design/25. The placeholder path stays, with the hold raised before any
supervised terminate and on renderer silence. The chaos spec now records every composited frame by default,
which caught and fixed a one-frame half-done crossfade after a restart.

Hardware-dependent items are unchanged: the WebGPU compositor, the venue soak, Synology DNS and certificate,
the Docker build, and the audio interface.
